# Bankwise Study Guide：先做出来，再真正学会

你不需要按 14 天排期逐行抄代码。现在先使用已经做好的项目，再按“能解释、能修改、能验证”的顺序学习。下面约 8–12 小时是学习时间估计，不是硬性期限；以过关标准为准。

## 0. 先知道自己拿到了什么（20 分钟）

这是银行营销分析项目，回答“哪些渠道/客群有不同的定期存款转化表现”。不是股票分析，不计算虚构收入，不预测贷款违约。数据来自真实公开数据集，但它是历史观察数据。

有两个不同入口：

- **预设演示**：选择菜单问题 → 固定 SQL → 真数据结果。无需 API，也不具备任意语言理解能力。
- **模型模式**：自己提问 → 模型根据 schema 生成 SQL → 程序检查、执行 → 失败后最多修复一次。需要 API Key，当前尚未真实调用验证。

先启动项目，依次运行整体、渠道、职业、收入问题，展开每个 SQL 和执行轨迹，下载一个 JSON。不要一上来读完所有代码。

**过关**：你能用 90 秒介绍用途、数据和两种模式，而且不会把演示菜单说成已测完的自然语言 Agent。

## 1. 数据口径比 SQL 更早（45–60 分钟）

阅读：`docs/DATA_CARD.md` → `bankwise/data.py`。

### 一行到底是什么

41,188 行不等于 41,188 个独立客户。源数据没有稳定客户 ID；我们生成的 observation_id 只是 1、2、3……行号。给记录起一个名字，并没有创造真实身份信息。

转化率 = `subscribed=1` 的观察记录数 / 所有观察记录数。总体为 4,640 / 41,188，约 11.27%。不要把“转化率提高 2 个百分点”和“相对提高 2%”混为一谈：10% 到 12% 是 2 个百分点、相对提高 20%。

`unknown` 是文本类别；`NULL` 是数据库缺失值，二者不同。`pdays=999` 是未曾联系的标记，不是实际等待 999 天。month 只有月份，没有逐行年份，把 May 与 June 排序并不能得到可靠的月度增长。

### ETL 在做什么

`prepare()` 下载 ZIP，读取其中的 CSV，转换整数/小数，把字段中的点号换成下划线，加入订阅标记，然后写 SQLite。先验证 41,188 行与 4,640 个正例，写入临时库后再替换正式库。`manifest.json` 保留来源与哈希，方便重现。

**练习**：解释为何不直接删除所有特征相同的行；找出三个会让分析失真的字段处理错误。

**过关**：不看文档解释行号≠客户 ID、unknown≠NULL、month≠完整时间序列，以及 duration 的信息泄漏。

## 2. 从 SELECT 到窗口函数（2–3 小时）

阅读：`bankwise/catalog.py`。在“SQL 工作台”运行下面查询。

### 从分子、分母开始

```sql
SELECT COUNT(*) AS observations,
       SUM(subscribed) AS subscriptions,
       ROUND(100.0 * AVG(subscribed), 4) AS conversion_pct
FROM bank_contacts;
```

0/1 的平均数等于 1 的比例。乘 100.0 输出百分比；不要在手写 `SUM/COUNT` 时不小心使用整数除法。

### 分组和样本量

```sql
SELECT job,
       COUNT(*) AS observations,
       SUM(subscribed) AS subscriptions,
       ROUND(100.0 * AVG(subscribed), 4) AS conversion_pct
FROM bank_contacts
GROUP BY job
HAVING COUNT(*) >= 100
ORDER BY conversion_pct DESC, job;
```

`WHERE` 在分组前筛行，`HAVING` 在分组后筛组。把 `WHERE subscribed=1` 写进这个查询再求 AVG，会让每组都变 100%；分母错了。

### CASE 把数值变成业务分组

查看 age/frequency 模板：CASE 将连续数值分段，再 GROUP BY。分段不是“模型自动发现规律”，它是分析者定义的口径。换边界会改变结论。

### CTE 和 ROW_NUMBER

阅读 `rank` 查询。第一层 segments 聚合渠道×职业并筛样本量；第二层 ranked 用 `PARTITION BY contact` 让每个渠道各自排名；最后取 position≤3。`ORDER BY conversion_pct DESC, job` 的第二项确保同分时顺序确定。

为什么不写 JOIN？因为真实数据就一张表。为了展示 JOIN 伪造客户表会破坏数据真实性。以后有真实多表数据再扩展；你仍需要额外练习 SQL JOIN 面试题。

**练习**：独立写“每个教育程度中，cellular 渠道的转化率，排除 unknown，至少 200 条记录”。再解释 WHERE/HAVING 顺序。

**过关**：不用 AI 写出上述查询；故意制造一次分母错误，解释为什么它错，并修复。

## 3. Python 怎样把数字变成证据（60–90 分钟）

阅读：`bankwise/insights.py` → `bankwise/evaluate.py` → `bankwise/agent.py` 中 `summarize()`。

先掌握 list、dict、for、函数、异常、上下文管理器。`DictReader` 逐行读 CSV，`defaultdict(list)` 把同一职业的记录装到同一组，`sum(row['y']=='yes' for row in group)` 计算成功数；Python 中 True 在这个求和里相当于 1。

评测为什么不直接再次执行同一段 SQL？那样可能把相同错误重复两遍。当参考答案由 CSV + Python 另一套路径算出时，才有更独立的交叉验证。也不是绝对真理：同一个人也可能在两条路径里重复同一个业务误解。

### 不要只看转化率

1/2=50%，500/1,000=50%，点估计相同，信息量不同。Wilson 区间给出描述性不确定性范围；不要求你手推公式，但应理解样本越少区间通常越宽。这个区间假设独立观察，无法修复混杂、选择偏差和重复客户问题。

程序摘要只读实际返回表，避免模型编造数字。“已返回结果中最高”指当前结果中的最高，不保证查询截断后的全局最高。

**练习**：在 Python 中比较 `wilson(1,2)` 与 `wilson(500,1000)`；描述区别。查看某组样本量后，提出需要哪些额外数据才能决定营销预算。

**过关**：解释为什么“最高转化率”“统计可靠”“业务值得投入”是三个不同问题。

## 4. Agent 的核心不是提示词很长（90 分钟）

阅读：`bankwise/agent.py` 的 `analyze()`，再读 `OpenAIPlanner`。

一条执行路径：

1. 检查问题是否为空、过长。
2. 读取真实表结构。
3. 演示模式选择固定计划；模型模式调用 API 生成 JSON 计划。
4. 计划可能是 query、refuse 或 clarify。
5. query 进入 SQL 执行器；成功就生成确定性摘要。
6. SQL/JSON 出错，把错误和上次 SQL 反馈给模型，最多再来一次。
7. 第二次失败就结束；网络或认证错误不会无穷重试。

`planner` 被作为参数传入，而不是在函数内部写死，这叫依赖注入。测试可以传入假的 planner：第一次返回错误列名，第二次返回正确 SQL，从而无需花 API 费用验证“修复流程”。但假的 planner 不能证明真实模型会写对 SQL。

schema 是列结构，不是整张数据。本版单表，不需要复杂 schema 检索。模型输出 SQL，不执行任意 Python。结果摘要由代码生成，因此少一次模型调用，也少一个编造数值的机会，但文字表达能力较有限。

**练习**：在 `tests/test_core.py` 找到 `test_repair`，用纸写出两次传入 planner 的 error 值与最终 trace。再解释 provider_error 为什么不自动改成 demo 答案。

**过关**：不用看代码画出完整状态流程，并说出真实模型未测试意味着什么。

## 5. 为什么“请只读数据库”远远不够（60–90 分钟）

阅读：`bankwise/sql.py` → 对应测试。

SQL 是需要执行的程序，不应只凭模型承诺决定权限。防线从语法到数据库逐层设置：

- AST 解析限制单条 SELECT、表名、非递归 CTE。
- 数据库以只读方式打开，同时设置 query_only。
- authorizer 限制实际读取对象和可调用函数。
- progress handler 限制指令数量和运行时间。
- fetchmany 限制输出行数并提示截断。

为什么只在 SQL 后面拼 `LIMIT 200` 不够？聚合和笛卡尔积可能先做大量计算，最后才 LIMIT。为什么字符串搜索 `DELETE` 不够？字符串、注释、语法变化使手工匹配很脆弱，解析器更了解语法，但仍需数据库权限兜底。

**练习**：运行正常 SELECT、DELETE、多条 SQL、读 sqlite_master、recursive CTE；查看测试如何确认库中记录仍存在。不要连接个人真实业务数据库做练习。

**过关**：讲清 SQL 注入/危险查询防护和“分析口径正确”是两件事。只读也可以算出错误结论。

## 6. 做一项独立改动（90–120 分钟）

任务：新增“是否曾被联系与本次转化的关系”。

验收要求：

1. 用 `pdays=999` 定义“此前未联系”，其余定义“此前联系过”。
2. 输出每组记录数、订阅数、转化率，不只输出一个百分比。
3. 加入 catalog，下拉菜单应自动出现。
4. 在 evaluate.py 中用 CSV/Python 独立计算预期值。
5. 运行测试和评测，解释记录数总和为什么应为 41,188。
6. 说明这个差异不能证明“之前联系导致本次转化”。

先独立做 30 分钟，再看 `docs/EXERCISE_HINTS.md`。不要只复制答案；把新增 SQL、参考答案和验证结果提交为你自己的第一次 Git commit。

**过关**：不用 AI 代写整个改动，能够定位失败并修复。这个比背诵 README 更能说明你理解项目。

## 7. 最后再准备面试（45–60 分钟）

阅读 `docs/INTERVIEW.md`，录制一次 3 分钟演示：问题 → SQL → 数字 → 边界 → 工程防护。面试官要求改需求时，现场修改一个分组查询。

诚实表达：“我使用 AI 辅助搭建项目，自己完成数据口径核对、代码理解、独立改动和测试验证。”在你还没做完这些之前，不要宣称完全独立开发，也不要把 15/15 演示测试写成 NL-to-SQL 100% 准确率。

## 完成学习的自测

以下每项都能独立做，才算真正掌握本项目：

- 从干净环境启动，解释下载、SQLite、网页三者关系。
- 手写 GROUP BY / HAVING / CASE 查询，解释窗口函数。
- 说出至少四个数据局限，并拒绝一个不可能回答的问题。
- 追踪模型失败后如何修复，区分网络失败、语法失败、语义错误。
- 解释防护层各自解决什么问题。
- 新增一个业务问题及独立答案评测，全部通过。
- 能讲清项目最重要的未完成项：真实模型效果和公共部署。

## 出错时怎么定位

| 现象 | 先检查 |
|---|---|
| python 无法运行 | Python 3.12 安装及 PATH，或使用虚拟环境解释器完整路径 |
| ModuleNotFoundError | 当前运行的 Python 是否就是安装 requirements 的那个 |
| 数据库不存在 | 在项目根目录执行 `python -m bankwise.data` |
| 首次下载失败 | 网络可否访问 UCI；已有交付数据可直接使用 |
| SQL 报列不存在 | 数据与口径页面的 schema，注意点号已改下划线 |
| 模型模式失败 | Key、模型 ID、账户额度和权限；不要把密钥贴到日志里 |
| 结果看起来不对但没报错 | 先核对分母、过滤条件、数据粒度，再考虑模型问题 |

学习顺序是：先会使用 → 能解释 → 能独立改动 → 有证据验证。无需等 14 天，也不要以“代码能跑”代替“自己学会”。
